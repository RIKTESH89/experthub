## Implemented policy

`isPreviewIsolated()` rejects external services when either runtime VERCEL_ENV is preview or the build-derived NEXT_PUBLIC_EXPERTHUB_PREVIEW_ISOLATED marker is true. next.config derives/overwrites that client marker from VERCEL_ENV, rather than accepting an inherited client false value. Runtime Preview cannot be weakened by a false marker. A Preview-built bundle remains disabled even if runtime metadata is missing. There are no opt-in provider-enable knobs in this slice. Production builds/runtimes retain existing behavior.

Razorpay SDK initialization and create/cancel handlers are blocked. Public signed webhooks reject before body/signature/provider receipt/database mutation work. Local verify remains read-only. Paid checkout client cannot load/create a gateway flow. Shared email delivery returns false without SDK initialization or recipient logging. Upload rejects before auth/form/S3/local fallback; post deletion can update staging DB but skips S3 cleanup. OpenAI generation, reranking, embeddings and shared extraction helpers guard raw fetches; chat/retrieval entry points also reject early. Background memory/personality/graph/indexing calls cannot bypass those shared boundaries. Web search returns no external results; blog imports reject before Jina/direct fetch (including fallback). Internal PostgreSQL lifecycle/cleanup work remains possible against the configured DB.

Google provider declaration is empty in Preview; server sign-in callback independently rejects Google, and login UI is visibly disabled. This is not a fake-auth option. Server/Edge/browser Sentry initialization, replay, reporting hooks and global-error capture are disabled. Preview bypasses withSentryConfig entirely, preventing build uploads/automatic monitor integration and the monitoring tunnel even with inherited-looking SENTRY_AUTH_TOKEN. Digest dispatch rejects in Preview; existing production secret/missing-secret behavior is deliberately unchanged and remains a separate production hardening concern.

## Static PostgreSQL 16 / pgvector review

There are 15 ordered migration SQL files. Their enum/table/index/FK/check/view/PLpgSQL/trigger SQL contains no identified PostgreSQL18-only feature. PostgreSQL16 supports the exact CREATE TRIGGER ... EXECUTE FUNCTION and PLpgSQL trigger patterns in EXP12/13 [PG16 CREATE TRIGGER](https://www.postgresql.org/docs/16/sql-createtrigger.html), [PG16 PLpgSQL triggers](https://www.postgresql.org/docs/16/plpgsql-trigger.html). This is a static conclusion, not executed compatibility proof.

Migration 20260323185226 creates vector extension, vector(1536), and HNSW cosine index. 20260323190303 drops that index immediately afterward; fresh migration still must successfully create the intermediate index. pgvector supports PostgreSQL13+, HNSW vector dimensions up to2000, and introduced HNSW in0.5.0: [official pgvector README](https://github.com/pgvector/pgvector), [official changelog](https://github.com/pgvector/pgvector/blob/master/CHANGELOG.md). Require installed/available vector extension at least0.5 with PostgreSQL16 support, CREATE EXTENSION privilege, and table/function/trigger DDL rights. Neon project's actual extension version/role rights were not inspected. No migration edits were needed or made.
