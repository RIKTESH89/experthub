# Compatible reader / gated writer rollout (proposed; no deployment performed)

EXP16_ENABLE_V2_WRITES is disabled unless its exact value is 1. With the flag unset or any other value, new publication emits persona-release-v1 plus additive approval audit metadata. The deployed 8897903 serving reader accepts that manifest: a native synthetic test executes its original serving source with only relative imports remapped to unchanged manifest/store dependencies. New readers continue to read v1 and v2 with the gate off. V2 rollback is blocked while writes are gated. Disabling the flag does not rewrite immutable history or change an existing v2 head.

1. Parent must review/build the repaired candidate and deploy it as a reader-compatible, writer-gated release with this flag unset. Confirm the authorized active-head inventory contains only v1 before treating the deployed v1-only binary as a downgrade target. No inventory query or deployment was run here.
2. Keep the flag off through reader rollout and acceptance. Establish and verify a separately retained deployable downgrade artifact containing the repaired v2-capable reader; the immediate previous binary should also be v2-capable before enabling the writer. This repair commit is source for such an artifact, not an already verified deployed target.
3. Enabling v2 writes requires the release owner's explicit selection of that tested downgrade target and authorized environment change. After a v2 head exists, v1-only binaries are invalid downgrade targets. Turning the flag off only stops further v2 activations; it does not make a v1-only binary compatible with existing v2 heads. Never delete or rewrite immutable releases/head history as a compatibility workaround.
4. Retained v1 content rollback remains owner-reviewed and subject to evidence/access/CAS checks; it is not automatic binary downgrade and cannot promise v2 frozen runtime behavior. Future releases must retain this reader contract or introduce an explicitly supported adapter.

Native proof uses PostgreSQL18 fixture tables, not the full old application binary/deployment or PostgreSQL16. A full combined build and authenticated/browser/provider acceptance are still parent gates. The tightened activation API requires preview approvalHash for both publication and rollback. Deploy its updated UI/API together; older clients safely fail validation rather than publishing unreviewed payloads.
