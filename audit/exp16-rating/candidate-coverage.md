## Implemented active path

1. Existing chat thumbs-up/down handler sends `{rating: 1|-1}` and now confirms an HTTP success receipt before reporting success to `POST /api/chat/sessions/[sessionId]/messages/[messageId]/rate`.
2. Route authenticates the actor, strictly validates rating-only payload, and returns the rating, linked review ID/state and immutable submission audit operation key. Malformed JSON returns 400.
3. Adapter verifies the saved assistant message/session/subscriber, derives its expert tenant, locks expert, parent session, then message and rechecks access. Rating, candidate and SUBMIT audit event commit in the same transaction.
4. The existing CorrectionReview workflow stores a feedback-only PENDING proposal. No source target, content, claim, evidence weight or belief is submitted by the rating. Both helpful and unhelpful ratings are candidates; neither is evidence of truth.
5. SUBMIT detail captures server-derived message/session IDs and at most 30 unique assertion support tuples from saved message source metadata. Each tuple is checked against EvidenceRevision -> EvidenceSpan -> EvidenceSupport -> EvidenceAssertion with both expert tenant constraints, source version, item and vector/chunk membership. No text, weights or asserted beliefs are copied. Owner-only, mismatched and foreign traces are omitted. Missing assertion traces, incomplete old-format traces or temporal-only saved provenance yields empty assertion references and still creates feedback for review.
6. Owner queue and review-workspace Decision history expose audit ID, saved message/session IDs and source/revision/span/assertion references. These are historical identifiers, not new clickable evidence endpoints or permission grants. Deleting support does not rewrite the immutable audit event. Live retrieval authorization remains independent.
7. Existing owner-only REJECT/REVISE/ACCEPT logic remains the decision path. A feedback-only rating cannot be accepted directly. An owner must separately revise into a complete changed manual-source proposal; acceptance retains existing source-version CAS, evidence retirement and outbox indexing behavior. Release creation remains separate.
8. Stable server key coalesces one review per actor/message/polarity. Repeats and alternation reuse the existing review, including terminal decisions, and never reopen it. Direct correction submissions cannot reserve the `rating:` key namespace. This intentionally does not capture every click as a separate event or allow a fresh rating review after a terminal decision; ordinary explicit feedback can create a new review.

## Concrete follow-up race fixes and compatibility checks

The previous rating adapter locked ExpertProfile and ChatMessage but read ChatSession ownership without holding its row lock. A concurrent session reassignment could invalidate authorization after the read. Both the rating adapter and the existing visitor-feedback submission helper now lock expert -> session -> message, then re-read and enforce subscriber/tenant/assistant-role checks. The direct-feedback helper also pins the initially locked session ID: a message moved to a different otherwise owned session cannot pass on an unlocked parent. Native barrier tests force these interleavings and confirm 403 with no candidate/audit/rating commit. Parent-first locking also agrees with ChatSession deletion’s child cascade; the native deletion interleaving completes without an orphan review or child-parent deadlock.

Review uniqueness remains `(expertProfileId, submittedBy, submissionKey)`; expert row serialization makes replay check/insert atomic for this service. Audit uniqueness remains `(expertProfileId, operationKey)`, and the composite `(expertProfileId, reviewId)` FK rejects foreign audit linkage. Saved support joins constrain both revision and assertion tenants, plus exact span/revision/item/version/chunk tuple. The schema permits some foreign assertion/span support pairs, but this rating query deliberately filters them; no graph/projection schema change was made. Terminal decisions remain terminal, and replay never promotes beliefs.

The React best-practices skill checklist was applied to touched components: typed props, unconditional hooks, event-driven request work, stable per-message pending lock, bounded timeout cleanup, no mutable shared server state, accessible pressed buttons/status/error/retry, no internal audit identifiers in chat, and no new provider/client bundle import.

Reusable native fixture setup for parent/EXP-14 assessment: `scripts/exp16-rating/run-native.py` with its config/setup and minimal integration fixture. It requires already installed PostgreSQL binaries and the ordinary execution approval flow in this sandbox. Each run gets a distinct `/tmp/exp16-rating-fixture-*` data/socket directory, disables TCP listening, creates only synthetic fixture tables, and stops/removes its server in `finally`. EXP-14 must use its own separately owned fixture and authorization, not reuse an active/shared cluster. This fixture is not evidence that EXP-14 projection SQL has been verified.

## P2 retrieval fallback compatibility repair

Independent review of `c293d97` found that default `retrieveIntentEvidence` creates authorized temporal-neighbor candidates without duplicated `knowledgeItemId`/`sourceVersion` in outer metadata. `assembleBundle` and `acceptedEvidence` preserve a complete saved assertion trace. The earlier rating normalizer required both outer duplicates, dropping the link (one selected assertion, zero links).

The rating adapter now derives item/version from the saved assertion trace; when an outer item/version property is present, it must still match exactly. Missing duplicates are supported; contradictory or null explicit pins, foreign tenant metadata, owner-only provenance, unrelated chunks and incomplete trace IDs remain rejected. The native SQL tenant/support/revision/span/item/version/chunk join is unchanged and remains the validation gate before audit persistence. Retrieval/projection internals were not edited.
