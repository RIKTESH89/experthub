## Implemented

Authenticated feedback creates a PENDING review and SUBMIT audit record only. Visitor submissions must reference an assistant message in their own expert-scoped chat, and cannot specify source changes. Owners can submit a complete correction, revise a pending proposal, accept, or reject. Reasons are required at the API. Expert identity is resolved from authenticated ownership, never request-supplied tenant fields. Queue/history is owner-only and bounded.

Owner decisions lock the expert and review, require expected review version, and accept only a currently existing manual source at the exact sourceVersion. Acceptance atomically increments the source version, updates title/content, revokes indexing eligibility, retires old evidence, and persists one revision-specific INDEX outbox job. Other sources remain unchanged. Existing lifecycle workers perform derivation later; acceptance makes no provider call. Original metadata/authorship/audience are preserved: approval is recorded as an expert decision, not fabricated original authorship. Source deletion leaves review/audit history; expert account deletion follows existing cascade retention behavior.

Per-expert operation keys plus request hashes support idempotent retries and reject changed requests. A decision is terminal after accept/reject; REVISE increments version and remains pending. Correction events and release manifests reject UPDATE in PostgreSQL. Events store actor, action, proposal, reason, original source snapshot/hash, resulting source version/hash, and serialized result. This protects application audit history; it is not a tamper-proof ledger against a privileged database administrator, and account deletion remains possible.

Persona releases store a stable SHA256 manifest: config including personalityProfile, identity snapshot, rendered owner/visitor persona prompts, sorted current source/evidence revision/snapshot/content hashes, vector IDs, evidence/temporal recipe versions, parent release and optional rollback target. Release construction requires all sources to have supported current published evidence; pending/stale/missing/unsupported evidence fails closed. Release head compare-and-set plus expert lock serializes concurrent releases. Rollback creates a new audit release and restores persona settings only if the target manifest hash validates and the entire evidence pin set is still current. It never restores historical source content/evidence/permissions. Changed, deleted, restricted, retired, or RAG-disabled evidence blocks rollback. Rollback does not change display name/specialty (identity snapshot records current profile).

## API and read contract

- GET/POST/PATCH /api/expert/corrections: bounded queue/events; create review with {submissionKey,proposal}; decision with {reviewId,expectedVersion,operationKey,action,reason,proposal?}. Proposal requires feedback; acceptance additionally requires itemId/sourceVersion/title/content. REVISE must precede acceptance of changed visitor content.
- POST /api/chat/corrections: {expertProfileId,messageId,submissionKey,feedback}; authenticated actor and message ownership enforced. Ratings still retain their existing behavior; no automatic rating-to-belief conversion.
- GET/POST /api/expert/persona-releases: owner-only manifest/history/head; create with {operationKey,expectedHead}; rollback additionally supplies rollbackTo. Null expectedHead means no prior head. 409 means stale CAS, incompatible key reuse, unfinished derivation, unsupported evidence or unsafe rollback.
- src/lib/persona/manifest.ts exports PersonaManifest, SourcePin, scopeForRelease. Consumers must resolve fresh RetrievalScope and fresh currentSourcePins per request, then use scopeForRelease as an intersection. Historical manifest never grants access. Existing authorizedEvidenceSpans/retrieveTemporalEvidence remain mandatory final live gates; this helper does not replace them. Existing interfaces/schema serving semantics are unchanged.
