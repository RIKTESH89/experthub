## Ownership and schema contract

Parent authorized this component to own migration `20261004000100_staging_webhook_inbox` and model `StagingWebhookInbox` in the normal Prisma ledger. This is migration 18; future parent integration must coordinate release wrapper expected count 17→18. No wrapper edits here. Migration CHECK constraints and partial due index are SQL-owned features Prisma cannot represent. No hosted migration was applied. Inbox is dedicated to Razorpay Test staging only, never production.

Public receiver rejects malformed signature headers and already-aborted requests before opening the reader; five-second abort-aware streaming deadline, 256KiB and 4096-read caps. Reader cancellation is best effort and never awaited indefinitely. It verifies HMAC on original Buffer before any JSON parse. SHA256 raw-body digest is the primary key; unsigned event-ID header is ignored entirely. The adapter resolves the INSERT only after its bounded database transaction commits. Authenticated malformed and unsupported payloads are durably acknowledged then processed/dead-lettered; invalid signatures never reach storage. Limit 256KiB. Wake callback is injected, best effort after commit; no timers, jobs, URLs or outbound relay are configured.

Restricted worker claims using one UPDATE with SKIP LOCKED, two-minute lease, random UUID fencing token, bounded exponential retries capped at 30 minutes, default eight attempts. Expired final attempt leases become dead. Business effects and inbox completion now share one transaction: lock/check inbox, invoke the shared transaction-aware reducer, then recheck token/state/lease using clock_timestamp() and mark done. Any final-check failure rolls back receipt, entitlement, counters, notification and billing outbox together. The public applyPaymentSnapshot API remains an unchanged wrapper around extracted applyPaymentSnapshotInTransaction; no domain logic duplicated. Crash before commit leaves no business effects; crash/lost reply after commit leaves a durable done inbox and one receipt.

Lock order is inbox → subscription → expert. Existing payment/cancellation/review paths acquire subscription → expert and never inbox. Claim SKIP LOCKED and contender tests verify no reverse ordering. Worker budget is 45 seconds including DB claim/apply/settlement. Adapter sets DB statement/lock/idle-transaction timeouts, Prisma transaction timeout and bounded pool wait; its deadline/abort race happens INSIDE the transaction callback and callers await rollback. Late callbacks retain only the closed tx client and cannot commit; no race around an independent mutating reducer. An unknown/timeout outcome returns503 with no inline retry. Recovery is by durable sweep. No protected Vercel relay.

Different serializations produce different receipts. Current shared reducer retains entitlement/counter/notification/outbox idempotency but increments billingVersion for each accepted distinct charge receipt. This is existing shared behavior, not claimed as exactly-once processing. Tests check this boundary and confirm that the second serialization invalidates the prior review CAS version (store rejects the stale plan; no reconciliation audit created). It can require a fresh admin review even without a changed paid interval. No automatic dead-letter replay, deletion or retention job; operators must review and approve recovery. Raw bodies may contain payment/customer metadata; plan access and retention before hosted use.
